# 跨平台 TUI 订单程序：大白话说明与 JSON 传递样例

依据：[4.md](4.md)。本文是该实现规范的教学说明，解释程序行为和数据传递，不表示现有代码已经全部实现。生产字段、接口契约和状态迁移以 4.md 为准；本文的教学辅助字段不能直接当作生产字段。下文均为模拟数据，不会执行交易，也不验证线上接口版本。

## 1. 这个程序到底干什么

这是一个支持 Windows 和 Linux、带 TUI（终端文本交互界面）的可执行程序。打开后在终端里用键盘操作，查看订单、调度进度、平仓任务和错误提示。可以把它理解成一个“自动接单、盯单、安排退出的管家”。

1. 启动时读本地 `orderlist.js`，恢复上次进度，并确认本次启动允许自动交易。
2. 到了信号刷新时间，先对旧的待开仓委托执行本轮停止与核实，再下载 GitHub 的 `size.txt`。核实不清的旧单保留，仅阻断对应目标的新开仓发布，不无限等待它而阻塞其他目标。
3. 检查信号格式和批次。同一合约、同一方向，最近 7 天已有成功开仓或部分成交后取消的记录，就跳过新开仓。
4. 合格信号先保存本地记录，再发布追踪开仓委托。Size 正数开多、负数开空，发出的 amount 保留正负号。
5. 每 60 秒查询已有订单。创建成功只是“交易所接单了”，不是“已经成交了”。
6. 开仓结束且确认有成交后，读取当前实际持仓，安排这个方向的总持仓平仓。如果已有旧平仓委托，先停掉、核实，再重新查询剩余持仓并计算新单。
7. 继续查询平仓委托，完成后归档。每个关键进度都写回 `orderlist.js`，重启后接着处理。

**信号刷新和状态查询是两只独立的闹钟。** 即使下载失败，已有订单仍然继续查询。旧开仓停止发生在下载之前，所以重复批次或下载失败也不会撤销已经发生的停止操作。

### 1.1 最后会拿到什么

最终需要交付两类产物，具体规范见 [4.md 第 1 节](4.md#1-范围与依据)：

| 交付物 | 怎么使用 |
| --- | --- |
| Windows、Linux 可执行文件 | Windows 使用 `orders3.exe`，Linux 使用 `orders3`；发布包提供必要依赖、配置示例和启动说明，无需自己编译，启动后进入 TUI |
| 发布在 GHCR 的 Docker container image | 拉取 `ghcr.io/<owner>/orders3:<version>`，通过 `docker run -it` 连接交互终端，使用同一套 TUI 和订单工作流 |

这里的镜像地址是发布格式，`<owner>`、`<version>` 要换成实际值；这份文档不表示程序已经构建或镜像已经上传。交付时须给出可执行发布包的获取位置与校验值、GHCR 镜像的版本地址与摘要，并说明支持的系统版本、CPU 架构及运行依赖。

Docker 镜像运行 Linux 版本；Windows 本机也有单独的原生可执行文件。Windows 上使用该镜像需要 Linux 容器运行环境。使用容器时，把存放 `orderlist.js` 的数据目录挂载到持久卷或宿主目录，并把 `storage_path` 指向那里，换容器后才能继续恢复进度。配置和密钥在运行时提供，不放进镜像；不要让本机程序和容器同时操作同一份恢复文件。

每次启动都在 TUI 中确认一次自动交易，容器也一样；没有交互终端或没有确认，就不能自动开始交易。界面会持续展示五类订单分组、任务和待核实原因，刷新界面不影响后台调度。退出时保存进度并恢复终端显示；退出程序不代表交易所里的委托已经撤销。

交付验收须在 Windows、Linux 和容器中分别检查界面操作、启动确认、状态刷新及重启恢复，并验证能从 GHCR 拉取镜像、重建容器后恢复挂载数据；这些检查使用模拟接口和测试数据。

## 2. 三类 JSON，不要混在一起

| 类型 | 大白话 | 发到哪里 |
| --- | --- | --- |
| 本地 request / response | 程序内部模块之间交接任务 | 本地模块 |
| HTTP 请求与原始响应 | 真正与交易所交互的数据 | 只把 HTTP 描述的 body 当作请求体发送 |
| `orderlist.js` | 程序的长期记事本，断电重启靠它恢复 | 本地磁盘 |

`size.txt` 下载下来是文本，要先解析成标准化 JSON。`orderlist.js` 虽然扩展名是 `.js`，里面也是严格 JSON，不是 JavaScript 程序。

本地标准化数据和持久化记录中，订单 ID、价格、金额、数量使用字符串；本地时间使用 UTC 毫秒整数；未知值使用 `null`，不能随便填 `0`。布尔值用 `true` / `false`。初始 `last timestamp=0` 是“尚未消费任何批次”的约定值，不代表一个未知订单时间。

交易所原始请求和响应遵循接口自己的类型约定。例如停止接口的 `body.id` 为 JSON 整数，原始 Position 的 `size` 可能为数值；适配器负责范围检查和无损转换，不经浮点数中转。HTTP 描述中的 `body=null` 表示不发送请求体，不能发送文本 `null`。

## 3. 先记住这几个编号

| 示例编号 | 用途 | 后续怎么传 |
| --- | --- | --- |
| `batch-1790053100000` | 这一批信号 | 关联批次和信号记录 |
| `signal-001` | 本地这笔开仓记录 | 开仓发布、开仓历史、平仓来源都引用它 |
| `req-open-001` | 一次本地发布请求 | response 原样回传 request_id |
| `intent-open-001` | 一次准备发单的意图 | 保存发什么、发到哪一步、是否收到回执 |
| `1118405` | 交易所开仓委托 ID | 用它查开仓 detail 或停止该委托 |
| `close-task-001` | 一次平仓安排任务 | 关联持仓快照、计算、平仓委托和来源 |
| `close-001` | 本地平仓记录 | 在待平仓和已完成平仓分组之间移动 |
| `1118500` | 交易所平仓委托 ID | 用它查平仓 detail，不能拿开仓 ID 代替 |

`target_key = BTC_USDT:LONG` 是同一目标的串行处理标识，不是订单 ID。本文沿用单账户、USDT、cross、dual_plus 的范围。

第 6 步代表经过若干轮查询后拿到成功终态，中间状态没有逐轮展开。这里 `evidence_complete=true` 仅表示已校验成功终态，足以归档成功开仓并触发总持仓平仓安排；单笔成交数量没有独立证据，仍为 `null`。它不表示所有成交及残余委托问题均已核实，也不能作为取消核实、恢复不明请求等其他操作的通用放行标志。判断证据是否充分必须结合当前操作及其核实条件。标准化 detail 的时间来源与转换后的时间在本步一并持久化。

第 9 步发送前先分配稳定的 `record_id=close-001`，并将它与任务、发布意图和确切请求内容关联后可靠保存；此时尚未建立带交易所 ID 的待平仓记录。收到可靠回执后，才在同一次提交中创建待平仓记录、保存交易所 ID，并更新意图及任务状态。若发送后未收到可靠回执或进程崩溃，依靠已保存的意图和任务恢复；先对账找回交易所 ID，再使用原 `record_id` 完成关联，不能另外创建一笔平仓委托。`before_http` 是教学说明，实际落盘的是发布意图、任务及其关联。

第 10 步能填写已平 `10`，是因为样例额外假设已核实持仓变化、排除了其他操作影响。`other_position_changes_excluded=true` 是本例的已知前提，不是看到仓位归零就自动设置的结果。实际运行应保存用于归因的订单状态、前后持仓快照、必要的关联成交信息及证据来源；不能排除其他操作影响时，本单精确数量继续记 `null`。

单笔数量能否确定与成功终态能否确认是两个判断。按 4.md 的 W5，校验 detail 成功状态和任务关联后，可归档成功并完成任务，同时查询 Position 记录当前持仓；不能仅因数量未知或账户仍有后来新增的仓位就否定原单成功。未知的单笔数量不强行补成覆盖数量或零；第 10 步中的数量和 `unfulfilled_quantity="0"` 仅展示证据充分的本例。

## 5. 每一步究竟接住了上一步什么

```text
size.txt 文本
  → 解析：合约、方向、价格、数量、批次时间
  → 保存 signal-001：一条待开仓记录
  → open.publish(input.record_id = signal-001)
  → 读取记录，生成 intent-open-001 和 HTTP body
  → 先保存 prepared，再保存 dispatching，然后发送
  → 收到 data.id = 1118405
  → 将 1118405 写进 signal-001.id，转入待开仓组
  → detail?id=1118405
  → 成功：保存 finish_time、trigger_price 和开仓历史
  → close.plan(source_record_ids = [signal-001])
  → 建立 close-task-001，查询 Position
  → 用当前持仓算平仓数量和激活价
  → close.publish(input.task_id = close-task-001)
  → 保存 intent-close-001 后发送
  → 收到 data.id = 1118500，建立 close-001 待平仓记录
  → detail?id=1118500
  → 核实成功，平仓记录归档，任务完成
```

**并不是把一个越来越大的 JSON 原封不动传遍所有接口。** 模块通常传 `record_id` 或 `task_id`，下一模块按编号读取已保存的数据；交易所只收到它需要的请求体。

例如开仓模块只收到 `{"record_id":"signal-001"}`，就能在本地找到 `signal_size="10"`，生成交易所需要的 `amount="10"`。交易所回传 ID 后，本地记录补上 `id="1118405"`，查询模块就知道该查哪笔委托。

## 6. 本地文件怎么变化

`orderlist.js` 的初始骨架是下面这个严格 JSON。最外层是只有一个对象的数组，分组名称中的空格需要保留。

```json
[
  {
    "schema_version": 1,
    "revision": 0,
    "last timestamp": 0,
    "raw orders": [],
    "pending open orders": [],
    "finished open orders": [],
    "pending close orders": [],
    "finished close orders": [],
    "batches": [],
    "publish_intents": [],
    "close_tasks": [],
    "terminal_history": [],
    "workflow_runs": []
  }
]
```

正常例子中，两条记录的去向如下。表中只展示编号，实际分组保存完整记录对象。

| 时刻 | raw orders | pending open orders | finished open orders | pending close orders | finished close orders |
| --- | --- | --- | --- | --- | --- |
| 信号入库 | signal-001 | 空 | 空 | 空 | 空 |
| 开仓发布成功 | 空 | signal-001 | 空 | 空 | 空 |
| 开仓成功结束 | 空 | 空 | signal-001 | 空 | 空 |
| 平仓发布成功 | 空 | 空 | signal-001 | close-001 | 空 |
| 平仓成功结束 | 空 | 空 | signal-001 | 空 | close-001 |

同一条记录是“移动分组”，不是同时复制到多个活动分组。平仓成功后，开仓历史仍然保留，用于 7 天去重和来源追溯。

其他数组也有实际用途：`batches` 记这一批接收、跳过、延迟了哪些信号；`publish_intents` 记发单进度；`close_tasks` 记平仓安排；`terminal_history` 记取消、撤换等历史；`workflow_runs` 记一轮流程进行到了哪里。

每次可靠提交都检查并更新 `revision`。一件事涉及多个字段时一起保存，例如“收到交易所 ID、意图 acknowledged、订单转组”，不能只保存其中一半。

## 7. 价格和数量怎么来的

**开仓数量看信号，平仓数量看实际持仓。** 本例信号 Size 是 `10`，所以开仓 amount 是 `"10"`。平仓时 Position 的 size 是 `10`，所以平仓 amount 是 `"-10"`。

如果原来有 10 张，本次又增加 2 张，平仓计算看重新查询得到的 12 张，不是只平本次的 2 张，也不能把 12 张写成本次开仓成交量。

本例多仓使用同一份持仓快照计算：

```text
E = entry_price = 100
V = value = 1000
M = initial_margin = 10
S = size = 10

V_adjusted = V = 1000
target_raw = 100 × (1 + 3.1 × 10 / 1000) = 103.1
target = 103.1 × 1.01 = 104.131
来源 trigger_price = "100.00"，保留 2 位小数
activation_price = "104.13"，使用 ROUND_HALF_UP
amount = -S = "-10"
```

持有空头仓位时（`S < 0`），`V_adjusted=-V`，最后乘 `0.99`；保留 V 原来的符号，不能擅自取绝对值。例如 `E=100、V=1000、M=10、S=-10`，来源价格为两位小数时，激活价为 `"95.93"`，平仓 `amount="10"`。这里的空头仓位不等于没有持仓：`S=0` 时不进行公式计算，按 4.md 的 W4 核实仓位变化原因后结束任务，不创建零数量单。

计算前须满足 `E>0、V≠0、M≥0、S≠0` 且持仓方向正确，计算结果及取整后的价格均须为正。多个来源合并时，取全部覆盖来源 `trigger_price` 的最大小数位数；字符串尾零也计入，例如 `"100.00"` 为两位。缺少或非正的 trigger_price 不能拿原信号价顶替，应保留任务及阻塞原因。

激活价不是保证成交价。`price_offset="1%"` 是追踪回撤设置，和计算公式里的 `1.01/0.99` 各自独立。按 4.md 的约定不额外调整价格步长；交易所明确拒绝就保存错误和任务。

## 8. 非正常情况，数据往哪走

| 遇到什么情况 | 保存什么、下一步干什么 |
| --- | --- |
| 开仓状态为 1 / 2 | 仍在待开仓组，继续等待激活或追踪 |
| 开仓状态为 3，部分成交 | 保存部分成交状态，等结束，暂不发布平仓 |
| 开仓状态为 5，确认零成交取消 | 归档 canceled_no_fill，不启动 7 天去重，不触发平仓 |
| 开仓状态为 5，确认部分成交取消 | 归档 partial_canceled，用 finish_time 启动去重，并安排平仓 |
| 取消单是否成交不清楚 | 保留待核实，不能拿原有仓位当作本单成交证据 |
| 创建成功拿到 ID，但 detail 暂时失败 | 保存原 ID，继续查这个 ID，不重新创建 |
| 发单超时，没有拿到 ID | 保存 unknown，先 list 找候选，再 detail 确认，Position 核对仓位 |
| list 找不到唯一且证据一致的订单 | 继续 unknown，不因第一页没找到或仓位没变就重发 |
| 旧平仓停止结果不明确 | 任务停在 reconciling_previous，不发替代单 |
| 旧平仓已停，新平仓被明确拒绝 | 将 `close_task.state` 保留或恢复为 `required`；下一轮状态调度恢复原任务，重新查询持仓、计算并验证后尝试发布 |
| 新平仓已经发布，后来被取消 | 核实后归档取消；未满足需求记 canceled_unfulfilled，不自动补发 |
| 存盘失败 | 停止后续会改变交易所状态的请求，恢复后先对账 |

创建结果不明时，本地响应例如：

```json
{
  "schema_version": 1,
  "request_id": "req-open-002",
  "operation": "open.publish",
  "outcome": "unknown",
  "result": {
    "intent_id": "intent-open-002",
    "exchange_order_id": null
  },
  "error": {
    "code": "CREATE_OUTCOME_UNKNOWN",
    "message": "请求已发出，但未取得可靠回执，先查询核实",
    "retryable": false
  },
  "next_action": "reconcile"
}
```

这里 `retryable=false` 表示不能直接再发一次创建请求，仍可继续只读查询。`request_id` 和 `text="apiv4"` 都不能当成交易所保证不会重复下单的凭据。

状态调度每 60 秒除查询订单外，还检查可恢复的延迟信号和未完成安排任务。这里“下一轮”指下一轮状态调度，不必等新信号到来。明确拒绝后的平仓重试沿用原 `task_id`，来源仍关联原任务，不重复生成安排任务；保留旧发布意图及错误，新的发送尝试另行记录发布意图。发送前仍须重新验证目标条件，并依次可靠保存 `prepared`、`dispatching`。条件仍不满足时保留待处理状态和原因；结果不明时只能先对账。

上述恢复不适用于 `canceled_unfulfilled`：已经成功发布、后来取消的平仓单不自动补发。它保留未完成需求，只有后续新的合格开仓来源才可再次触发总持仓平仓安排。

## 9. 最容易理解错的几条规则

- **7 天从详情里的 `data.order.finish_time` 算。** 本例 `"1790053200"` 秒转成 `1790053200000` 毫秒；满 `604800000` 毫秒才允许同目标新开仓。不是从信号时间、查询时间或创建响应时间算。时间缺失、为零或在未来时，仍保存已确认的开仓历史和待平仓需求，但阻断同目标新开仓；平仓所需证据及计算字段齐全时继续安排，不因去重时间异常而一并停下。`trigger_price` 缺失或非正则阻断依赖它的平仓计算，不能回退到原信号价。
- **同合约多空分别去重。** BTC 多仓历史不会直接拦住 BTC 空仓信号；同一目标的修改必须串行。
- **批次已消费不等于其中信号均已发布。** 新批次的接收、跳过、延迟决定与 `last timestamp` 一次保存，全部被去重也消费批次。相同批次不重复导入，旧批次不倒着处理。因旧单未核实等条件而延迟的信号保留在 raw 组，并记录 deferred 决定及原因；阻塞解除后，由状态调度重新检查是否已被新批次替代、执行 7 天去重及发布前校验，通过才发布。
- **新批次只能替代确认尚未发送的旧 raw 信号。** 替代时归档并保留原因，已有 `prepared` 意图也须核实仍未发送并阻止其后续发送。`dispatching/unknown` 不能当作“没拿到 ID 就是没发过”，必须保留并先对账。替代与发送在同一目标下串行，避免旧信号在被替代后仍发出。
- **平仓安排由新的、已结束且有成交的开仓来源触发。** 单纯价格、保证金变化，或已发布平仓被取消，不会自动触发重新安排。
- **有旧平仓时，先停止、核实，再重新查询仓位计算。** 停止过程中可能已经成交，不能用停止前的数量继续下单。仓位已零也要核实变化原因，确认后结束任务。
- **平仓单发布后，覆盖数量固定。** 后来又增加仓位，不会修改旧平仓单的 covered_quantity；原单成功后账户仍有仓位，也不能直接认定原单失败。
- **重启先恢复，不从空白开始。** `dispatching` 时崩溃按结果不明处理；文件损坏不能用空文件覆盖。唯一恢复依据是 `orderlist.js`，日志不能代替它。
