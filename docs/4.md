# 订单自动管理：C++ / JSON 工作流与跨平台 TUI 交付规范

## 1. 范围与依据

本文将 [3.md](3.md) 转换为以 C++ 为实现基础的 request、response、持久化模型与状态机规范，不表示功能已实现。业务规则以 3.md 和用户本次确认为准；接口形状参考 [orders2](test/orders2/README.md) 与 [test_response.md](test_response.md)。本文不执行交易。

用户已确认：

- 产品为带 TUI（终端文本交互界面）的 C++ 可执行程序，支持 Windows 和 Linux；最终交付两类产物：各平台可执行文件，以及发布在 GHCR（GitHub Container Registry）的 Docker container image。
- 7 天去重时间使用详情接口 `data.order.finish_time`，不使用成交接口 `finish`、单笔 Orders Times 或查询时间；成功开仓和部分成交后取消均适用。
- 开仓数量取自 GitHub size.txt 的 Size：正数开多、负数开空，创建开仓时 amount 保留 Size 的正负号；零数量拒绝。此项按用户确认的业务规则实现，不再设方向待验证开关。
- list 用于查找订单和恢复丢失的订单 ID，detail 用于查询指定订单的状态，Position 用于获取当前实际持仓及平仓计算数据；具体核实边界见第 5.6 节。
- 激活价沿用本文公式与小数位规则，不额外进行价格步长校验或调整；交易所明确拒绝时保存原始错误。

本文的 request/response 包装是本地 C++ 模块协议，不是交易所新增接口；只有 HTTP 描述中的 body 作为请求体发送。标准化 JSON 与交易所原始响应明确分开。未提供完整证据的接口不虚构路径或字段。

注意：样例取消订单也有 finish_time。它是本业务选定的去重起点，不单独证明成交，也不能冒称为实际最后成交时间。

### 1.1 产品形态与最终交付

程序启动后进入 TUI，在终端内提供键盘操作、状态展示和本次启动的自动交易确认。界面至少展示调度状态、五类订单分组、平仓任务、待核实请求及错误原因；界面刷新不得阻塞网络查询、调度或可靠存盘。TUI 调用本文的本地模块协议，不直接绕过状态机修改订单或发送交易请求。

最终交付要求如下，均为待实现、待验收的要求：

| 产物 | 平台与要求 |
| --- | --- |
| 原生可执行文件 | 分别构建 Windows 的 `orders3.exe` 和 Linux 的 `orders3`，启动后提供同一套 TUI 和业务功能；发布包附带必要运行依赖、配置示例及启动说明，用户无需自行编译 |
| Docker container image | 封装同一程序的 Linux 版本，发布到 `ghcr.io/<owner>/orders3:<version>`；提供明确版本标签及对应镜像摘要，并说明与可执行文件版本的对应关系 |

原生 Windows 和 Linux 运行均必须支持，不以容器运行代替任一平台的原生可执行文件。发布说明列明实际支持的操作系统版本、CPU 架构及运行依赖；GHCR 的 `<owner>` 和 `<version>` 在发布时替换为实际命名空间和版本。

容器通过交互终端（`docker run -it`）使用 TUI；Windows 宿主使用该 Linux 镜像时需具备 Linux 容器运行环境。`orderlist.js` 所在数据目录通过持久卷或宿主目录挂载，并将 `storage_path` 指向挂载目录，容器替换后仍可恢复。配置及密钥在运行时注入，不打包进镜像；原生与容器实例不得同时写入同一份恢复数据。容器每次启动也须完成本次自动交易确认，未连接交互终端或未确认时不得自动开始交易。

### 1.2 构建与发布验收

构建流程须分别产出 Windows、Linux 可执行发布包和 Docker 镜像；镜像构建成功不等于完成 GHCR 发布。交付时提供两个平台发布包的获取位置、校验值，以及可从 GHCR 拉取的版本化镜像地址和摘要。

使用模拟接口与临时数据验收两个原生平台及容器的 TUI 启动、键盘交互、启动确认、状态刷新和重启恢复。另验证 GHCR 镜像拉取、交互终端运行以及容器重建后的挂载数据恢复。退出时可靠保存进度并恢复终端状态，不将退出程序视为交易所委托已撤销。

## 2. JSON 通用约束

使用 UTF-8 严格 JSON，无注释、尾逗号、NaN/Infinity。orderlist.js 虽使用 .js 后缀，内容仍是 JSON，不执行 JavaScript。

| 数据 | JSON 类型 / C++ 类型 | 约束 |
| --- | --- | --- |
| 订单、任务、请求 ID | string / std::string | 非空；交易所 ID 原样保存，不经 double 中转 |
| 价格、金额、数量 | string / 精确十进制类型 | 不使用 float/double 做业务计算；价格保留尾零 |
| 本地时间 | integer / std::int64_t | UTC 毫秒；未知为 null |
| 布尔值 | boolean / bool | 不使用字符串 true/false |
| 仓位方向 | string / enum class | LONG、SHORT |
| 业务方向 | string / enum class | Open Long、Open Short、Close Long、Close Short |
| 交易所状态 | integer | original_status 的 1～5；其他值保留原值并待核实 |

本规范限定单账户、USDT、cross、dual_plus。`target_key = contract + ":" + position_side`。扩展多账户或模式时，必须将账户及模式加入隔离键，不能混合去重或持仓。

必填字段缺失、类型错误、溢出、方向冲突均返回结构化错误。外部响应可保存未知字段；本地不认识的 schema_version 禁止加载后覆盖。数量按合约约束验证，不假设所有合约允许小数张数。

## 3. 配置、启动及调度

本地配置示例；具体运行时刻由配置决定：

```json
{
  "schema_version": 1,
  "storage_path": "orderlist.js",
  "signal_schedule": {"kind": "interval", "interval_seconds": 60},
  "status_poll_seconds": 60,
  "dedupe_window_ms": 604800000,
  "signal_url": "https://raw.githubusercontent.com/huan00000/price/refs/heads/main/size.txt",
  "exchange": {"host": "https://api.gateio.ws", "prefix": "/api/v4", "settle": "usdt"},
  "strategy": {"price_offset": "1%", "price_type": 3, "pos_margin_mode": "cross", "position_mode": "dual_plus"},
  "dedupe_time": {"field": "data.order.finish_time", "unit": "seconds", "rule_confirmed": true},
  "open_direction_rule": "signed_signal_size"
}
```

其他调度形式为 `{"kind":"daily","time":"09:00:00","timezone":"UTC"}` 或 `{"kind":"weekly","weekday":1,"time":"09:00:00","timezone":"UTC"}`。weekday 为 ISO 1～7。时区显式配置，同一调度点只执行一次，错过多轮不集中补发；上一轮未完成不叠加。

启动顺序：加载并验证 orderlist.js → 本次启动确认一次自动交易 → 对账已有 ID、在途意图和不明请求 → 开启调度器。确认不跨进程重启复用；运行中停止、开仓、平仓不逐单要求 YES。

信号调度和状态调度独立计时。状态调度每 60 秒运行，即使没有新信号或下载失败也继续。同目标所有变更串行；不同目标可以独立推进。文件损坏不能用空文件覆盖，旧格式需备份后迁移。

## 4. 本地 request / response 契约

通用请求示例：

```json
{
  "schema_version":1,
  "request_id":"req-open-001",
  "operation":"open.publish",
  "target_key":"BTC_USDT:LONG",
  "requested_at_ms":1790053131000,
  "input":{"record_id":"signal-001"}
}
```

通用成功响应：

```json
{
  "schema_version":1,
  "request_id":"req-open-001",
  "operation":"open.publish",
  "outcome":"succeeded",
  "result":{"record_id":"signal-001","exchange_order_id":"1118405","group":"pending open orders"},
  "error":null,
  "next_action":"order.poll"
}
```

结果不明响应：

```json
{
  "schema_version":1,
  "request_id":"req-open-002",
  "operation":"open.publish",
  "outcome":"unknown",
  "result":{"intent_id":"intent-002","exchange_order_id":null},
  "error":{"code":"CREATE_OUTCOME_UNKNOWN","message":"请求已发出但未取得可靠回执","retryable":false},
  "next_action":"reconcile"
}
```

outcome 枚举：succeeded（本次操作已完成）、skipped（按业务规则跳过）、deferred（等待条件）、rejected（明确拒绝）、unknown（外部副作用不明）。创建操作 succeeded 不代表已经成交。响应必须回传 request_id。

retryable 表示是否可以重新执行副作用请求，不限制只读查询。超时、连接中断、服务端错误、回执无法解析不能自动判为创建失败；只有能证明未创建的明确拒绝才进入安全重试路径。

| operation | input 核心字段 | result 核心字段 |
| --- | --- | --- |
| runtime.start | 本次确认结果 | 恢复数量、待核实目标 |
| signal.refresh | 调度时间 | batch_id、accepted/skipped/deferred 数量 |
| open.publish | record_id | exchange_order_id、group |
| order.stop | exchange_order_id、reason | stop_accepted、verification_state |
| order.poll | exchange_order_id | original_status、execution、next_action |
| close.plan | target_key、source_record_ids | task_id、state |
| close.publish | task_id | exchange_order_id、covered_quantity |
| reconcile | intent_id 或 exchange_order_id | resolved、证据引用 |

## 5. 交易所 HTTP 请求与响应

以下协议来源于本地参考资料，不宣称已验证当前交易所版本。实现时适配器须校验请求语义。密钥从运行环境读取，不写入订单文件和日志。

### 5.1 签名

沿用 orders2/general.py 的签名结构：

```text
payload_hash = hex_lower(SHA512(实际发送的 body UTF-8 字节；GET 为空串))
sign_text = METHOD + "\n" + "/api/v4" + path + "\n"
          + query_string（不含 ?）+ "\n" + payload_hash + "\n" + Timestamp
SIGN = hex_lower(HMAC_SHA512(API_SECRET, sign_text))
headers = Accept: application/json, Content-Type: application/json,
          KEY: API_KEY, Timestamp: 签名中同一个秒时间字符串, SIGN: 签名
```

C++ 序列化 body 一次，用同一字符串签名和发送。HTTP 描述 body=null 表示无请求体，不能发送文本 null。签名 query 的编码、顺序必须与 URL 实际字节一致；认证请求不跨域重定向。

### 5.2 创建追踪委托

以下开多报文参考原样例，仅说明结构，不是实际交易指令：

```json
{
  "method":"POST",
  "path":"/futures/usdt/autoorder/v1/trail/create",
  "query":"",
  "body":{
    "reduce_only":false,"contract":"BTC_USDT","amount":"1",
    "activation_price":"100","is_gte":false,"price_type":3,
    "price_offset":"1%","pos_margin_mode":"cross",
    "position_mode":"dual_plus","text":"apiv4"
  }
}
```

参考成功响应：

```json
{"code":0,"message":"ok","data":{"id":"1118405"},"timestamp":1790053131375}
```

成功判据：HTTP 200/201、code 为数字 0、data.id 有效。立即保存 ID，然后使用同一个 ID 查询详情。详情失败不重新创建。所谓成功响应缺失 ID 按 unknown 处理；timestamp 是响应时间，不能作为开仓去重时间。

| 业务方向 | reduce_only | amount | is_gte | 当前依据 |
| --- | --- | --- | --- | --- |
| Open Long | false | GitHub Size 原值，Size > 0 | false | 用户确认的数量正负规则 |
| Open Short | false | GitHub Size 原值，Size < 0 | true（orders2） | 用户确认的数量正负规则 |
| Close Long | true | -S，S > 0 | true | 3.md 规定 |
| Close Short | true | -S，S < 0 | false | 3.md 及参考响应 |

开仓以 GitHub 信号 Size 的正负确定方向，amount=signal_size，不取绝对值。Side 用于一致性校验，若与 Size 矛盾则报错；无需额外方向验证开关。Side 是本地方向，不自行添加为交易所请求字段。text=apiv4 和本地 request_id 均没有已证明的交易所幂等能力。

### 5.3 停止追踪委托

```json
{"method":"POST","path":"/futures/usdt/autoorder/v1/trail/stop","query":"","body":{"id":1118433}}
```

参考 stop.id 为 JSON 整数；本地字符串必须范围检查后转换，禁止 double 中转。超出适配器确认范围则拒绝发送。

实际失败样例：

```json
{"code":-1,"message":"Failed to terminate","timestamp":1790054301741}
```

成功响应结构摘录：

```json
{"code":0,"message":"ok","data":{"order":{"id":"1118433","original_status":5,"status_code":"cancelled","finish_time":"1790054490"}},"timestamp":1790054490614}
```

code=0 不代表子订单全部撤销或没有成交。无论停止响应如何，必须查询 detail 和 Position，按第 5.6 节核实后决定后续；停止失败或不明时保留记录并阻断对应目标替代发布。

### 5.4 详情查询

```json
{"method":"GET","path":"/futures/usdt/autoorder/v1/trail/detail","query":"id=1118433","body":null}
```

参考 pending 响应结构摘录：

```json
{
  "code":0,"message":"ok",
  "data":{"order":{
    "id":"1118433","contract":"BTC_USDT","amount":"1",
    "original_status":1,"status_code":"pending","status":"open",
    "created_at":"1790054385","finish_time":"0","trigger_price":"",
    "suborder_id":"0","pos_margin_mode":"cross","position_mode":"dual_plus"
  }},
  "timestamp":1790054426629
}
```

校验 code、返回 ID、合约、方向及模式。业务分支使用 original_status，status_code 用于交叉核对；允许 canceled/cancelled 拼写归一，状态矛盾则待核实。status=finished、finished_at 非零、activated_at_precise 非空不能单独证明成交。

时间转换：created_at 和 finish_time 按样例秒字符串解析为 int64 后乘 1000，检查溢出；finish_time="0" 标准化为 null。单位由适配契约明确，不按数字长度猜测，不依赖未定义的 *_precise。实际接口单位不符合适配契约时拒绝转换。

### 5.5 持仓与合约查询

```json
{"method":"GET","path":"/futures/usdt/positions/BTC_USDT","query":"","body":null}
```

持仓响应直接为对象或对象数组，不套用 trail 的 code/data 结构。以下为公式演算用模拟数据：

```json
[{"contract":"BTC_USDT","mode":"dual_long","pos_margin_mode":"cross","size":10,"entry_price":"100","value":"1000","initial_margin":"10"}]
```

按 contract + mode（dual_long/dual_short）+ pos_margin_mode 唯一匹配，另核实账户 position_mode=dual_plus。样例同时存在 cross/isolated，不能只按合约和方向匹配后任取一项。原始 size 可为数值，标准化为精确十进制字符串，不经 double 损失精度。

```json
{"method":"GET","path":"/futures/usdt/contracts/BTC_USDT","query":"","body":null}
```

合约响应直接为对象。校验交易状态和数量限制。本程序不额外校验 activation_price 的价格步长，不使用 order_price_round 或 mark_price_round 改写激活价。按既定公式及小数位规则提交；若交易所明确拒绝价格，则保留任务及原始错误，不擅自调价。

### 5.6 使用 list、detail 与 Position 核实订单和恢复请求

优先参考 [test_response.md](test_response.md) 中的 detail、Position 和 trail/list 样例。本程序按当前整个方向持仓安排平仓，不要求每次先枚举全部历史成交。

- 有交易所订单 ID：用该 ID 查询 detail，核对合约、方向、模式和 original_status；再查 Position 获取当前实际持仓。详情暂时失败仍保存原 ID，继续查询，不重新创建。
- Position 的 size 是该合约、该方向、该保证金模式下当前持仓数量，平仓 amount=-size；entry_price、value、initial_margin 用于公式。它不是某一笔订单的独立成交量，也不是追踪订单 ID。例如原有 10 张、这次增加 2 张，Position 显示的是 12 张，平仓按 12 张安排。
- detail=4 按本地参考资料认定该委托成功完成，记录成功历史并查询 Position 安排平仓；不再强制先取得全部成交明细。单笔精确成交量没有证据时记 null，不能用总持仓冒充。当前持仓为零时按 W4 核实并结束任务。
- detail=3 记录部分成交状态并继续等待结束。detail=5 时结合之前的 partial 状态、detail 和前后持仓快照判断是否有成交。只在能够排除其他开平仓或人工操作影响时，才把持仓差额归到本单；原来已有持仓不能证明本次取消单成交。无法判断时保留待核实。
- 创建超时且没有收到 ID：先用 trail/list 查找候选并取得 ID，再用 detail 确认，同时查询 Position 核对实际持仓。匹配时结合本地发布意图中的合约、开平方向、amount、激活价、账户模式和发送时间范围；只有唯一且证据一致的候选才绑定 ID。Position 本身不能返回这笔追踪委托的 ID；仓位没变也可能是委托尚未触发，不能据此认定未创建后直接重发。
- trail/list 的响应数组位于 data.orders。参考资料未给出完整过滤及分页请求定义；不得把第一页未找到当作未创建，也不能仅凭合约、价格相同绑定订单。无法唯一找回时保留 unknown，不重复发单。

ExecutionResolver 汇总 list、detail 与 Position 的核实结果，保存订单状态、持仓快照、数据来源和待核实原因。filled_quantity、closed_quantity、remaining_quantity 等单笔数量未知时允许 null；remaining_working_quantity 未知也为 null，不伪填 0。evidence_complete 表示当前业务步骤的证据充分，不等于已查遍所有历史成交。若 detail 与 Position 仍不足以确认取消成交或残余委托，再补充关联子订单/成交查询；缺少 suborder_id 不能单独证明没有成交或没有残余委托。

### 6.1 订单记录

待发布开仓模拟记录：

```json
{
  "record_id":"signal-001","tag":"raw orders","id":null,
  "batch_id":"batch-1790053100000","batch_at_ms":1790053100000,
  "Contract":"BTC_USDT","side":"Open Long","position_side":"LONG",
  "target_key":"BTC_USDT:LONG",
  "signal_price":"100.00","signal_size":"1","signal_value":"100",
  "trigger_price":null,"requested_amount":null,
  "local_state":"ready","original_status":null,
  "created_at_ms":null,"trailing_finished_at_ms":null,
  "dedupe_at_ms":null,"dedupe_time_source":null,
  "execution":{"filled_quantity":null,"remaining_working_quantity":null,"evidence_complete":false},
  "terminal_result":null,
  "close_assignment":{"state":"not_eligible","task_id":null},
  "source_record_ids":[],"last_error":null
}
```

字段约束：

- record_id 为稳定本地 ID，id 为交易所 ID；同一 record_id 只能位于一个活动分组。
- 不复用旧 timestamp 多种含义，批次、创建、追踪结束、去重和实际最后成交时间分开保存。
- signal_price 与 trigger_price 分开。trigger_price 是触发价，不是平均成交价；不得由轮询覆盖原信号价。
- finished open orders 的 terminal_result 为 success、partial_canceled、canceled_no_fill；前两种参与去重，第三种不参与。
- finished close orders 仅放核实成功完成的记录；取消/撤换放 terminal_history，保留成交量、来源、任务和原因。
- 平仓记录额外必填 task_id、source_record_ids、covered_quantity、closed_quantity、remaining_quantity。covered_quantity 为已确定的非负十进制字符串；closed_quantity、remaining_quantity 未确定时为 null，已确定时为非负十进制字符串；发布后 covered_quantity 不随账户新持仓改变。
- 已成交但时间或 trigger_price 缺失也必须保存历史与待平仓需求。缺去重时间阻断同目标新开仓；不影响证据已完整的其他平仓步骤。

### 6.2 发布意图

```json
{
  "intent_id":"intent-001","request_id":"req-open-001",
  "operation":"open.publish","record_id":"signal-001","task_id":null,
  "target_key":"BTC_USDT:LONG","state":"prepared",
  "prepared_at_ms":1790053131000,"exchange_order_id":null,"attempt":1,
  "http_request":{
    "method":"POST","path":"/futures/usdt/autoorder/v1/trail/create","query":"",
    "body":{"reduce_only":false,"contract":"BTC_USDT","amount":"1","activation_price":"100.00","is_gte":false,"price_type":3,"price_offset":"1%","pos_margin_mode":"cross","position_mode":"dual_plus","text":"apiv4"}
  },
  "response":null,"last_error":null

```

意图状态：prepared → dispatching → acknowledged / rejected / unknown。

prepared 已可靠落盘且按协议尚未发送；发送前先持久化 dispatching。进程在 dispatching 崩溃，恢复按 unknown 对账，即使实际可能没发出去。acknowledged、订单 ID、转组和关联必须同次提交。保存精确请求体字节或哈希便于核对；不保存密钥与签名。

{

source_record_ids 为此次新增触发来源；covered_source_record_ids 为累计覆盖来源，含被撤换任务仍有关联的来源，用于精度计算和追溯。一项来源只触发一次安排；轮询不能反复生成任务。新来源到达时，先核实在途任务，再串行合并或建立后续撤换任务。

任务状态：required、checking_position、stopping_previous、reconciling_previous、ready、publishing、unknown、active、completed、canceled_unfulfilled、blocked。

## 7. 标准工作流

### W0：恢复与串行

orderlist.js 是订单、历史、任务、意图及操作进度的唯一恢复依据；数据库和日志只能作为可重建输出。prepared 按发送协议处理；dispatching/unknown 先对账；有 ID 的记录继续查询该 ID。

同 target_key 的停止、创建、转组串行，signal.refresh 自身也不重入。不明目标继续只读核实并阻断替代单，不影响无关联目标。

### W1：信号刷新

固定顺序：停止旧 pending 开仓 → 核实 → 下载 → 校验 → 批次判断 → 去重 → 原子保存 → 发布。

1. 遍历旧 pending 开仓，对可停止订单保存停止进度并调用 stop，按第 5.6 节查询 detail 与 Position；有成交进入统一平仓，无成交取消归档，不明保留旧记录。
2. GET signal_url，无签名。响应是文本而不是 JSON。下载或解析失败不消费批次、不覆盖旧数据。
3. Orders Times 必须唯一并解析为 UTC 毫秒；每个信号块均须完整校验 Symbol、Price、Side、Size、Value，不得仅接受正则匹配到的一部分。价格正、数量非零、数值有限、方向与源符号一致。
4. 本规范对同批次重复 Contract + Side 采用整批拒绝并报 DUPLICATE_TARGET，不更新批次；同合约多空分别处理。
5. 来源时间等于 last timestamp 为 DUPLICATE_BATCH，小于为 STALE_BATCH，只有大于才导入。即使重复、旧批次或下载失败，前面停止操作也已发生。
6. 同 Contract + Side 的 success/partial_canceled 历史，满足 `0 <= now_ms - dedupe_at_ms < 604800000` 时拦截。满 7 天放行；缺时间、未来时间或未核实成交则 deferred，不猜测放行。
7. 新批次、接收/跳过/延迟决定、raw 记录及 last timestamp 一次保存，全部去重也消费批次。旧批次未提交 raw 标记 superseded 归档；dispatching/unknown 旧请求继续核实。
8. 目标旧单未核实时新信号保留 raw/deferred；核实后重做 7 天去重再发布。信号刷新不停止旧平仓。

标准化信号示例：

```json
{
  "batch_id":"batch-1790390566354","batch_at_ms":1790390566354,
  "orders":[{"Contract":"SOL_USDT","side":"Open Short","position_side":"SHORT","signal_price":"125.45","signal_size":"-1","signal_value":"-143.03"}],
  "validation":{"complete":true,"duplicate_targets":[]}
}
```

batches 保存 batch_id、源时间、每项 record_id 和 accepted/skipped/deferred 决定及原因；原始文本或其摘要可附存以供追溯。

### W2：发布开仓

锁目标 → 确认信号未被新批次替代 → 重新去重 → 校验合约、模式及 Size/Side 一致性 → 构建 body → 保存 prepared → 保存 dispatching → create → 保存结果。

成功时 raw 转 pending open，同时保存 ID 与 acknowledged；明确拒绝保留 raw/rejected，重试前重新验证条件；unknown 保留意图并阻断目标。创建成功后的详情失败不重新发布，不使用样例中另一笔订单 ID 查询本单。

### W3：开仓轮询

| original_status | 行为 |
| --- | --- |
| 1 pending | pending open / waiting_activation，继续轮询 |
| 2 ongoing | pending open / tracking，继续轮询 |
| 3 partial | 保存部分成交状态及可确认的数量，等待结束，不提前发布平仓 |
| 4 success | 校验 detail 后归档 success，标记 close_assignment=required，再查询 Position 安排实际持仓平仓 |
| 5 canceled | 核实后，零成交归档 canceled_no_fill；有成交归档 partial_canceled 并标记 required |
| 未知、失败、矛盾 | 保留 pending / reconciling，不推断终态 |

按第 5.6 节以 detail 终态和 Position 核实结果推进，不把单笔精确成交量或全部成交分页作为成功订单安排总持仓平仓的前置条件。取消订单仍须判断是否有成交及残余委托，不明时保留核实状态。部分成交取消不要求成交量等于原数量。

成功及部分成交取消都设置 `dedupe_at_ms = parse_int64(detail.data.order.finish_time) * 1000`。dedupe_time_source 保存字段路径、原值、单位。finish_time 缺失、零或异常时保留待核实，阻断依赖该历史的同方向新开仓。不能回退到成交 finish、取消查询时间或批次时间。

### W4：按当前整个方向持仓撤换平仓

触发条件仅为“开仓已结束、有成交、尚未安排”的来源。仅价格/保证金变化或已发布平仓取消不触发。

1. 同目标合并待处理来源，生成/恢复一个任务并原子关联；来源改为 assigned_to_task，避免每轮重复安排。
2. 初步查询唯一且模式正确的持仓。停止该目标旧 pending 平仓，通过 detail 核实追踪终态，通过 Position 核实剩余持仓；有残余委托疑点时按第 5.6 节补充核实。
3. 任何旧单未明则 reconciling_previous，不创建替代单；核实后重新查询持仓，用此时剩余整个方向仓位计算，不沿用停止前数量。
4. 保存新发布意图再创建；成功时 pending close、task=active、来源安排标记及旧任务关联同次保存。旧单按实际完成或取消/撤换归档。
5. 明确创建失败保留 required，下轮重新查询持仓计算；unknown 先对账。新单成功发布不删除开仓历史。
6. 持仓已零时核对成交及其他仓位变化原因，确认后结束任务，不创建零数量单。

公式仅使用同一次持仓快照的 E=entry_price、V=value、M=initial_margin、S=size：

```text
V_adjusted = (S > 0) ? V : -V
target_raw = E * (1 + 3.1 * M / V_adjusted)
target = target_raw * ((S > 0) ? 1.01 : 0.99)
scale = max(全部 covered_source_record_ids 对应 trigger_price 的小数位数)
activation_price = ROUND_HALF_UP(target, scale)，保留 scale 位尾零
amount = -S
price_offset = "1%"
```

保留 V 原符号，不能改为 abs(V) 或 -abs(V)。E>0、V≠0、M≥0、S≠0 且方向正确，target 和取整后价格均正。trigger_price 缺失/非正不得回退到信号价。本程序不额外做 tick size 校验或调整；按上述小数位提交，交易所明确拒绝时保存错误及任务，不擅自调价。

模拟多仓计算及请求：

```json
{
  "calculation":{"entry_price":"100","value":"1000","initial_margin":"10","size":"10","value_adjusted":"1000","target_raw":"103.1","target":"104.131","source_price_scale":2,"activation_price":"104.13"},
  "request":{
    "method":"POST","path":"/futures/usdt/autoorder/v1/trail/create","query":"",
    "body":{"contract":"BTC_USDT","amount":"-10","reduce_only":true,"activation_price":"104.13","is_gte":true,"price_type":3,"price_offset":"1%","text":"apiv4","pos_margin_mode":"cross","position_mode":"dual_plus"}
  }
}
```

相同 E/V/M、S=-10、来源两位小数时，平空激活价为 "95.93"、amount="10"、is_gte=false。仅验证公式，不证明示例合约接受该价格。固定回撤 1% 与公式 1.01/0.99 为独立设置，激活价不是保证成交价。

### W5：平仓轮询

1/2 继续等待；3 保存可确认的已平量和剩余量，未知为 null；4 校验 detail 成功状态及任务关联后进入 finished close，并查询 Position 记录当前剩余持仓。发布后新增仓位不改变原 covered_quantity，不能因账户未归零就判原任务未完成。

5 按第 5.6 节通过 detail、Position 及必要补充查询核实已平量、残余委托及持仓，归档取消/撤换；有未完成需求设置 canceled_unfulfilled 并保留原因，不自动补发，不记为成功完成。即使取消时覆盖量已满足，也保留取消终态事实及覆盖满足证据。以后新开仓来源可再次触发总持仓平仓。

“旧单已停，新单明确创建失败”仍是未完成安排 required，可重试；“已成功发布的新单后来取消”不自动回 required。

### W6：可靠保存与重启

转组、批次消费、意图、任务关联须一次提交：独占文件锁 → 校验 revision → 候选快照 → 同目录临时文件完整写入 → 刷盘 → 原子替换 → 更新内存。失败不能使用未提交快照继续发单。

Windows 使用适当原子替换及 FlushFileBuffers；POSIX 使用文件 fsync、rename 和必要目录同步。单实例进程锁防止多进程同时发送；std::mutex 只解决进程内并发。网络查询可不持文件锁，但提交须验证版本，过期响应重新核实，不能覆盖新状态。

workflow_runs 保存 run_id、kind、phase、待停止 ID、每目标核实进度、已处理批次；停止发送前也记录进度，崩溃后先查询该 ID，不能假设请求没发出。日志不是恢复依据。7 天失效不代表可删除仍被任务引用的历史。

## 9. 错误处理与验收

| 错误码 | 动作 |
| --- | --- |
| SIGNAL_PARSE_ERROR / DUPLICATE_TARGET | 不消费批次 |
| DUPLICATE_BATCH / STALE_BATCH / DEDUPE_7D | skipped；新批次去重决定一并保存 |
| FINISH_TIME_INVALID / DIRECTION_CONFLICT | 阻断依赖条件的发布，继续核实已有单 |
| STOP_UNVERIFIED / EXECUTION_INCOMPLETE | deferred，保留 pending 和任务 |
| POSITION_NOT_UNIQUE / POSITION_MODE_MISMATCH | 保留任务，不下单 |
| INVALID_DECIMAL | 保留任务，报告字段；价格被交易所明确拒绝时按 CREATE_REJECTED 保存原始错误 |
| CREATE_REJECTED | 保存明确拒绝，重试前重算并校验 |
| CREATE_OUTCOME_UNKNOWN | 对账，禁止直接重发 |
| CLOSE_CANCELED_UNFULFILLED | 保留未完成需求，不自动补发 |
| STORE_COMMIT_FAILED | 停止后续副作用请求，恢复后对账 |

实现验收使用模拟 HTTP 和临时文件，不需要真实下单：

1. 第 6 天同方向拦截，恰好 604800000 ms 放行；反方向独立。去重仅使用 detail.finish_time，修改 Orders Times 不影响结果；未来/缺失时间不放行。
2. partial 不安排平仓；部分成交取消经核实后平仓并启动去重；零成交取消不启动去重。
3. 创建成功而详情失败保留 ID；创建超时、回执丢失、写盘失败先对账，重启不重复发布。
4. 停止后下载失败/重复批次保留停止结果，状态轮询持续；全部信号去重仍消费批次。
5. 同目标多来源只形成一个总持仓任务；两位/四位触发价合并按四位；不额外做价格步长校验；交易所明确拒绝价格时保留任务和原始错误。
6. 旧平仓未核实不得创建替代单；停止期间成交，新单使用重新查询后的剩余持仓。
7. 新平仓明确创建失败保留 required；已发布后取消保留 canceled_unfulfilled，不自动补发。
8. 新增账户仓位不改变旧任务覆盖量；cross/isolated 并存时唯一正确匹配。
9. 所有持久化断点重启不丢批次、历史、来源关联和不明请求；其他输出不能覆盖 orderlist.js。
10. 每次启动只确认一次；同目标两个调度器并发不重复创建；GitHub Size 正数开多、负数开空，amount 保留符号；Size 为零或与 Side 矛盾时报错。
11. Position 总持仓不冒充单笔成交量；有 ID 时 detail 恢复原单，无 ID 且 Position 未变化时仍不能直接重发；取消成交无法归因时保留待核实。

本次用户确认整理如下，前文相关配置、流程与验收已同步调整：

1. **开仓看 GitHub 信号数量。** size.txt 的 Size 为正就开多，为负就开空；amount 直接保留该数量的符号。Side 只做一致性检查，不再把方向映射列为待验证阻断项。
2. **实际要平多少，看 Position。** 按合约、方向、保证金模式找到当前持仓，用 size 确定平仓数量，用 entry_price、value、initial_margin 计算激活价。这里需要的是当前总持仓，不强求先算清每笔历史订单成交多少；Position 的总持仓不写成单笔成交量。
3. **恢复订单用 list、detail 和 Position 配合。** 有订单 ID 就查 detail；没有 ID 时先用 list 找候选订单、恢复 ID，再用 detail 确认，Position 用来核对当前实际仓位。list 匹配结合本地请求的合约、方向、数量、激活价、模式和发送时间范围；找不到唯一订单时保留待核实，避免重复下单。取消单是否有成交不明时也保留核实，不把旧仓位当作本次成交。
4. **激活价不额外处理步长。** 按既定公式和小数位规则生成、提交，不额外查询或套用 tick size；如果交易所明确拒绝，则记录错误、保留任务，不自动改价。这是本程序的处理约定，不表示交易所一定没有价格限制。

仅在现有 list/detail/Position 无法解决具体核实问题时，补齐必要的列表过滤分页或子订单/成交关联接口，不再将它们作为所有正常流程的统一前置条件。本文保留完整价格公式，3.md 对 4.md 的引用对应第 7 节。
